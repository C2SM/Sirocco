Definitions of different terms and concepts in the Sirocco terminology

---

### configuration directory
Directory containing the `sirocco.yaml` file and all files needed to configure the tasks (software configuration files, scripts, source code, ...). Relative paths in the [configuration](configuration/configuration.md) are resolved from it and it is the positional argument of the `sirocco` CLI. The standalone [engine](#engine) runs the workflow in place: it creates the `run` directory, hosting the task [run directories](#run-directory), and the `sirocco.log` file inside it.

### coordinates
Set of values identifying a specific instance of a [task](#task) or [data](#data) among all instances sharing the same name in the unrolled graph. Coordinates are the instance [date](#date), if it belongs to a recurring [cycle](#cycle), and the values of the [parameters](#parameter) attached to it. They are reflected as well in the task [run directory](#run-directory).

### cycle
Set of potentially recurring tasks sharing a common periodicity, declared in the [`cycles`](configuration/cycles.md) section. The recurrence is given by a start date, a stop date and a period, all in ISO 8601 format. Without this information, the cycle is a _one-off_ cycle, happening only once. Each repetition is called a [cycle occurrence](#cycle-occurrence).

### cycle occurrence
One repetition of a [cycle](#cycle), spanning from its occurrence start date to its occurrence stop date. The last occurrence ends exactly at the cycle stop date, even if it is shorter than the cycle period.

### data
Piece of information stored on a file system and produced by a piece of software, represented as a node in the workflow graph. Human written files used to configure a task (_e.g._ a FORTRAN namelist) are not data but part of the [workflow configuration](configuration/configuration.md). Data is either **available**, _i.e._ existing before the workflow starts, or **generated** as an [output](#outputs) of a task. Data properties are declared in the root level [`data`](configuration/data.md) section while their relationships to tasks are described in the [`cycles`](configuration/cycles.md) section.

### date
Attribute of a [cycle occurrence](#cycle-occurrence) and of the task and generated data instances belonging to it. By convention, it is the occurrence start date. It is one of the [coordinates](#coordinates) of these instances and is used to target them with [`target_cycle`](configuration/cycles.md#target_cycle).

### engine
Component orchestrating the execution of a workflow. The **standalone engine** runs autonomously on the HPC system, relying on the scheduler as the sole running daemon, while the **AiiDA engine** (under development) runs on a dedicated server. See [Orchestration](orchestration.md).

### inputs
[Data](#data) instances consumed by a [task](#task), grouped by [port](#port) in the task `inputs` specification of the [`cycles`](configuration/cycles.md#inputs) section. An input which is generated by another task induces a dependency between the two tasks.

### outputs
[Data](#data) instances produced by a [task](#task), grouped by [port](#port) in the task `outputs` specification of the [`cycles`](configuration/cycles.md#outputs) section. Only generated data can be outputs.

### parameter
Named sequence of values declared in the root level [`parameters`](configuration/parameters.md) section and attached to tasks and data. One instance of a parameterized task or piece of data is created for each combination of the values of its parameters (full matrix). When targeting a parameterized node in the [`cycles`](configuration/cycles.md#parameters) section, each parameter is resolved with a _targeting mode_: `single` (same value as the current task) or `all` (all values, the default). Typically used for ensemble or sensitivity experiments. See [Parameters](configuration/parameters.md).

### plugin
Implementation of the actual behavior of a [task](#task), selected with the `plugin` task specification. Sirocco currently provides the general purpose [`shell`](plugins/shell.md) plugin and the [`icon`](plugins/icon.md) plugin, dedicated to the ICON model.

### port
Named role that one or several pieces of data play for a given task. [Inputs](#inputs) and [outputs](#outputs) are specified as mappings from port names to sequences of data, which can be understood as a formal equivalent of command line arguments. Ports allow tasks to use data unambiguously without making assumptions on the behavior of other tasks. The port names `link` and `link_content` are [reserved](configuration/cycles.md#special-input-linking-ports).

### rank
Position of a task in the dependency structure of the workflow. The _global rank_ $R$ is the index of the [topological generation](orchestration.md#the-deep-propagating-submitted-task-front) the task belongs to. The _local rank_ $r$ locates the task with respect to the [task front](#task-front): $-1$ for completed tasks, $0$ to $d-1$ for tasks within the front, $d$ for not yet submitted tasks.

### run directory
Directory in which a task instance runs. With the standalone engine, it is located at `run/<task_rundir_name>` under the [configuration directory](#configuration-directory), where `<task_rundir_name>` is built from the task name and its [coordinates](#coordinates).

### task
Unit of work submitted as a job to the HPC scheduler and represented as a node in the workflow graph. Its content (scheduling information, scripts, configuration files, ...) is declared in the root level [`tasks`](configuration/tasks.md) section and its behavior is implemented by a [plugin](#plugin). Its place in the graph is described in the [`cycles`](configuration/cycles.md) section. The special `ROOT` and `SIROCCO` tasks respectively provide default settings for all tasks and settings for the Sirocco continuation task of the standalone engine.

### task front
Set of tasks currently running or submitted ahead-of-time to the scheduler, organized in $d$ dynamical generations, where $d$ is the [`front_depth`](configuration/configuration.md#front_depth). As tasks complete, the front propagates through the graph by submitting new tasks with adequate scheduler dependencies. See [the deep propagating submitted task front](orchestration.md#the-deep-propagating-submitted-task-front).

### wait_on
Explicit dependency between tasks, added on top of the ones derived from [inputs](#inputs) and [outputs](#outputs) relationships. Typically used to prevent tasks from running too early. See [`wait_on`](configuration/cycles.md#wait_on).

### workflow
Directed acyclic graph of [task](#task) and [data](#data) instances obtained by unrolling the [cycles](#cycle) and [parameters](#parameter) described in the `sirocco.yaml` file of a [configuration directory](#configuration-directory).
